# Одноразовый перенос замен и прав

Старые данные не переносятся при загрузке кода в GitHub. Инструмент ниже только читает Netlify и создаёт приватную копию JSON + SQL. Он не удаляет и не меняет данные старого сайта. Его зависимости отделены от основного проекта и не используются Cloudflare.

## Перед переносом

1. Создайте новую D1 и выполните `npm run db:remote` по основной инструкции.
2. Договоритесь с администраторами временно не менять замены/права: экспорт нескольких объектов не является единой транзакцией на старом хостинге.
3. Не выдавайте права и не редактируйте замены в новой production-базе до импорта. Импорт намеренно **не перезаписывает** существующие месяцы и список прав. Для испытаний используйте отдельную тестовую базу.
4. Сохраните прежний `AUTH_SESSION_SECRET` в секретах Cloudflare, если он не был скомпрометирован. Это сохраняет сопоставление авторов замен; при смене секрета старые `_actor` больше не сопоставляются, понадобится повторный вход.

## Экспорт

Из корня проекта:

```sh
npm install --prefix tools/netlify-export
```

Создайте **в корне** приватный `.env.migration`, используя образец `tools/netlify-export/.env.example`:

- `NETLIFY_SITE_ID`: Project ID старого сайта в Netlify → Project configuration → General → Project information.
- `NETLIFY_AUTH_TOKEN`: временный Personal Access Token с доступом к этому проекту. Не присылайте его в чат и не сохраняйте в Git.

```sh
node --env-file=.env.migration tools/netlify-export/export.mjs
```

Команда напечатает только количество записей и папку вида `private-backups/export-.../`. Внутри:

- `records.json`: полный снимок нужных записей, включая revision и закрытые идентификаторы авторов.
- `import.sql`: SQL для импорта в уже созданную таблицу D1.

Экспортируются все месяцы `schedule-replacements` и `site-permissions/grants-v1`. Кратковременный онлайн-список не переносится — он появится при посещении нового сайта. Токены Google, cookie и локальные отчёты инструмент не читает.

Если команда завершилась ошибкой, **не переключайте DNS**. Проверьте наличие обоих файлов и успешное сообщение. Сохранённый JSON можно использовать для восстановления; неполный/непроверенный SQL не импортируйте.

## Импорт

Сначала при желании проверьте SQL на локальной базе, используя фактический путь из сообщения экспорта:

```sh
npm run db:local
npx wrangler d1 execute DB --local --file="private-backups/export-<НОМЕР>/import.sql"
```

После проверки базы назначения и резервной копии выполните один раз:

```sh
npx wrangler d1 execute DB --remote --file="private-backups/export-<НОМЕР>/import.sql"
```

Проверьте количество строк (запись — месяц или список прав, а не одна пара):

```sh
npx wrangler d1 execute DB --remote --command="SELECT namespace, COUNT(*) AS records FROM site_records GROUP BY namespace"
```

Сопоставьте количество с экспортом и проверьте содержимое через интерфейс сайта. Повторный импорт не заменяет существующие ключи; **это не синхронизация**. Если новую базу уже использовали, не удаляйте записи ради импорта — потребуется отдельное объединение данных.

## После переключения

Проверьте замену/отмену в двух браузерах, права администратора и Classroom. Только затем отключите старый сайт и отзовите временный токен Netlify. Удалите приватный `.env.migration`, когда он больше не нужен, и храните резервную копию вне публичного репозитория. Экспорт содержит Google email пользователей с выданными правами; обращаться с ним нужно как с персональными данными.

При том же домене браузерные черновики и настройки сохраняются. При смене origin их нужно переносить через экспорт/импорт редактора. Не очищайте localStorage ради переезда.
